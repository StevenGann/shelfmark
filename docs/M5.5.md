# M5.5 — Label capture (DigiKey and Mouser)

Stock only becomes real when things arrive. Every DigiKey bag carries a Data
Matrix label that already says what the part is, how many there are, the lot and
the date code. Reading it is faster and less error-prone than typing, and it is
the difference between a system that tracks inventory and one that documents it.

## What the label actually contains

Decoded from real DigiKey labels with zxing-cpp, the Data Matrix is an ANSI
MH10.8.2 message: `[)>` + RS, then GS-separated fields of *application
identifier* + value.

```
[)>␞06␝P296-OPA211AIDRGRCT-ND␝1POPA211AIDRGR␝30P296-OPA211AIDRGRCT-ND
   ␝KCAN AND THERMOMETER␝1K99932782␝10K127846989␝9D2524+5␝1T5397196ML5
   ␝11K1␝4LDE␝Q25␝11ZPICK␝12Z26564848␝13Z999999␝20Z000000000…
```

| AI | meaning | example |
|----|---------|---------|
| `06` | customer part number, DigiKey prefixes it with `P` | `P296-OPA211AIDRGRCT-ND` |
| `1P` | manufacturer part number | `OPA211AIDRGR` |
| `30P` | supplier part number (DigiKey PN) | `296-OPA211AIDRGRCT-ND` |
| `1V` | manufacturer, as Mouser sends it | `TI`, `KOA Speer` |
| `14K` | supplier line item | `003` |
| `K` | item description | `CAN AND THERMOMETER` |
| `Q` | quantity | `25` |
| `9D` | date code | `2524+5` |
| `1T` | lot | `5397196ML5` |
| `4L` | country of origin | `DE` |
| `10K` | purchase order | `127846989` |

The linear Code 128 barcodes on the same label are DigiKey-internal references
(`019514918`); they identify an order line, not a part. They are recorded in the
scan result but never used for matching.

## Definition of done

1. A photo of a DigiKey label can be uploaded from the browser and decodes to
   DigiKey PN, MPN, description, quantity, lot, date code and country.
2. A decoded label resolves to an existing part by DigiKey PN first, then by
   MPN; an unknown part can be created from the scan in the same form.
3. Confirming a scan records a stock receipt at a chosen location, with the lot
   and date code in the move's note.
4. The location defaults to where that part was last put away.
5. A photo with no readable barcode says so plainly and offers the manual form.
6. The same decode is available from the CLI for a file, with no browser.
7. Nothing writes until a human confirms.

## Decoding

Server-side, in `app/labels.py`, using `zxing-cpp` and Pillow:

- Accept JPEG, PNG or WebP up to 20 MB. Reject other types by magic bytes.
- Try Data Matrix, Code 128, QR, Code 39 and PDF417, with rotation, downscale
  and denoise enabled. A 4096×3072 phone photo decodes at 40% scale, so the
  decoder downsamples before giving up.
- If several symbols are found, prefer the MH10.8.2 Data Matrix; fall back to a
  Code 128 whose payload matches a DigiKey part-number shape
  (`*-ND`, `*-CT`, `*-TR`, `*-DKR`).
- If nothing usable is found, the response is **422** with the raw payloads that
  *were* read, so a wrong label is distinguishable from a blurry photo.

## Parsing

`parse_label(raw)` returns:

```python
{
  "digikey_pn": "296-OPA211AIDRGRCT-ND",
  "mpn": "OPA211AIDRGR",
  "description": "CAN AND THERMOMETER",
  "quantity": 25,
  "lot": "5397196ML5",
  "date_code": "2524+5",
  "country": "DE",
  "purchase_order": "127846989",
  "raw": "[)>…"
}
```

Unknown AIs are preserved in a `fields` dict rather than dropped, because the
label format will change and the next person should not have to re-derive it.

## Resolution

`resolve_label(conn, parsed)` answers "what is this, and where does it live":

1. `digikey_pn` against `part_link.sku` where the distributor is DigiKey.
2. `mpn` against `part.mpn_norm` — exactly one part, or none.
3. Nothing → `status: "unknown"`, with a prefilled create-part form.

The result carries the part's IPN, MPN, manufacturer, current stock rows, and
`suggested_location`: the location of that part's most recent `receive`, or
`None` when it has never been stocked.

## API

| method | path | notes |
|--------|------|-------|
| `POST` | `/api/labels/decode` | multipart `file`; decode + resolve; writes nothing |
| `POST` | `/api/labels/receive` | multipart `file` (re-decoded server-side, never trusted from the client) + `location`, optional `quantity`, `note`, and `create_part=true` with `manufacturer` for an unknown part |

Both are `engineer`. The receive endpoint records a `receive` move whose note is
`lot <lot>, DC <date_code>` when those are present, so traceability survives
without a lot schema.

Creating a part from a label also stores the DigiKey PN as a distributor link
with its SKU, so the next scan of the same product resolves immediately.

## CLI

```
shelfmark label scan --file label.jpg
shelfmark label receive --file label.jpg --location "Drawer A" [--quantity 25]
```

## Interface

A **Scan label** panel on `/stock` and on the part page:

- `<input type="file" accept="image/*" capture="environment">` — on a phone this
  opens the camera, on a desktop it opens a file picker.
- After upload: the decoded fields, the matched part (or "new part" fields), a
  location input pre-filled with the suggestion and a datalist of known
  locations, a quantity input pre-filled from the label, and a Confirm button.
- Errors sit above the form: "No barcode found in that photo — try again with
  the label filling the frame." with the manual entry form still available.

## Out of scope

Lot-level stock rows (the ledger note carries it), expiry, OCR of the printed
text when the barcode is unreadable, and batch import of a reel of labels.

## Tests

Fixtures are generated with `zxingcpp.create_barcode` inside the tests, so no
photograph of a real shipment is committed to a public repository. Cases:

- a full MH10.8.2 Data Matrix parses to every field
- a Code 128 carrying only a DigiKey PN resolves by part number
- an image with no barcode returns 422 and lists what it saw
- a known DigiKey PN resolves to the part; a known MPN resolves when the PN is absent
- an unknown label offers creation and creates the part with its SKU link
- receive writes a `receive` move and the note carries lot and date code
- `suggested_location` is the last receive location
- a viewer gets 403 on both endpoints


## Mouser

Mouser sends the same ANSI MH10.8.2 Data Matrix with a different set of fields:

```
[)>␞06␝KQUAD ADC, THERM,R"␝14K003␝1PTMP118MBIYMSR␝Q20␝11K091050594␝4LCN␝1VTI␞␄
```

- `1V` names the manufacturer, which DigiKey never sends — so a Mouser label
  prefills the manufacturer field instead of asking for it, and `1V` is also how
  the two suppliers are told apart (`06` is empty on both).
- DigiKey's own part number lives in `P`, not `06`. On a Mouser label `P` is the
  position list (`6-8,11,13-4`), so a value containing a comma is never taken
  as a part number.
- There is no `30P`, and `06` is often empty, so the supplier part number comes
  from the linear Code 128, which carries `<3-digit mfr id>-<mpn>`
  (`660-RN73H1ETP1001F25`).
- **Some Mouser labels omit `1P` entirely.** The KOA bag in the house has no
  manufacturer part number in the 2D symbol at all; the only copy is in the
  linear code. The parser therefore reads the Code 128 payloads as well, and
  derives the MPN by stripping the three-digit prefix — but only when the
  payload is not a DigiKey part number, whose identical shape ends in `-ND`,
  `-CT`, `-TR` or `-DKR`.
- The message ends with `RS` `EOT`; those bytes are stripped from the last field.

### When the 2D symbol will not read

A small or angled label often yields only the linear codes. That is still worth
prefilling: the supplier part number and MPN come from `595-TMP118MBIYMSR`, the
quantity is the largest short integer (`20`, not the `003` line item) and a
two-letter payload is the country. The form is prefilled, nothing is written,
and the human confirms — a photo with no readable symbol at all still returns
422 with the payloads that *were* read, so a bad angle is distinguishable from
a wrong label.

Resolution is by supplier part number across **any** distributor (`part_link.sku`),
then by MPN. A bag scanned from either supplier resolves to the same part once
its link is stored.
