# M1.8 — Assets a human can supply

The queue handles what DigiKey will hand over. It cannot handle a supplier that
blocks automated downloads, a part that never came from a distributor, or a
photo that is simply wrong. Those are the cases where a person standing at the
bench knows more than the fetcher does, so the part page has to accept files.

## Definition of done

1. An engineer or admin can upload a datasheet and an image from the part page.
2. A viewer cannot. The route answers 403, not a redirect.
3. Uploads are validated by content, not by filename or the browser's claim.
4. An upload replaces the existing asset of that kind, and the enrichment queue
   never overwrites it afterwards.
5. Uploads land in the same `SHELFMARK_ASSET_DIR` tree as fetched assets, so the
   NFS mount and the backup story stay the same.
6. The page says who supplied the file and when.
7. Mobile: the file input is reachable and tappable at 390 px without zoom.

## Storage and schema

`migrations/0006_asset_uploads.sql` adds three columns to `part_asset`:

| column              | meaning                                              |
|---------------------|------------------------------------------------------|
| `source`            | `digikey` (fetched) or `upload` (supplied by a human) |
| `uploaded_by`       | username, NULL for fetched assets                     |
| `original_filename` | the name the uploader saw, for the record             |

`source` defaults to `digikey` so existing rows are correct without a rewrite.

Layout is unchanged — `parts/<ipn>/datasheet.<ext>` and `parts/<ipn>/image.<ext>`
— except that the extension follows the real content: `pdf` for datasheets;
`jpg`, `png` or `webp` for images. `rel_path_for()` gains an extension argument
rather than assuming one file extension per kind.

An upload's `source_url` is `upload:<username>:<sha256 prefix>` so the existing
`UNIQUE (part_id, kind, source_url)` still holds and the row records its origin.

## Validation

The browser's `Content-Type` and the filename are both advisory. The bytes
decide:

- **Datasheet**: must begin with `%PDF-`. Stored as `application/pdf`.
- **Image**: JPEG (`\xff\xd8\xff`), PNG (`\x89PNG\r\n\x1a\n`) or WebP
  (`RIFF....WEBP`). Stored with the matching type.

Anything else is refused with a message naming what was expected. A 3 KB HTML
error page saved as `datasheet.pdf` is the exact failure this rule exists for.

Size caps: **25 MB** datasheet, **10 MB** image. Enforced while streaming, not
by trusting `Content-Length` — a client can lie about that and the pod has a
2 GiB limit to respect. The temp file is removed on every failure path.

## Replacement and the queue

Uploading deletes the existing rows for that `(part, kind)` and writes one new
row. The previous file is replaced in place by the atomic `os.replace`.

`enrich.run_enrichment` skips any kind whose current asset has
`source = 'upload'`. A human override stays put until a human removes it; the
queue must not quietly undo bench knowledge on the next pass. Re-fetching is a
deliberate act: the page offers "remove upload" which deletes the row and the
file, and the next enrichment run fills the gap again.

## Interface

On `/parts/{ipn}`, beside each asset:

```
Image     [photo]         [Choose file] [Upload]   uploaded by sydney, 25 Nov 2026
Datasheet [datasheet]     [Choose file] [Upload]   uploaded by sydney, 25 Nov 2026
```

A single form per kind, `enctype="multipart/form-data"`, `accept="application/pdf"`
or `accept="image/*"`. The submit button is a full-height 44 px target; the
input is 16 px text. Errors re-render the page with the message above the form
and the file input cleared — never a JSON body in an HTML page.

`POST /parts/{ipn}/assets/{kind}` with the file field `file`. On success:
303 to `/parts/{ipn}`. Errors: 400 (wrong type, too large, empty), 403
(viewer), 404 (unknown part or kind). `DELETE /parts/{ipn}/assets/{kind}`
removes an upload and redirects back.

## Out of scope

Multiple datasheets per part (revisions), image galleries, and uploading BOMs.
One part, one datasheet, one photo — the same rule the fetcher already follows.
