# M3 — BOM ingest from KiCad

The through-line is "KiCad project → BOM → parts → stock". This milestone builds
the left half: a project, its revisions, and BOM lines that point at parts.

## Definition of done

1. A KiCad BOM CSV can be imported against a named project, from the UI or the
   API, and never silently replaces an earlier revision.
2. Importing the same file twice produces no second revision.
3. A line whose MPN matches a part is linked automatically; a line that matches
   nothing is kept as an unmatched line with the reason, not dropped.
4. Every import shows a diff against the previous revision: added lines,
   removed lines, quantity changes, reference changes.
5. A KiCad footprint overrides the supplier package string on the part.
6. Unmatched lines can be resolved one at a time, or in bulk by creating parts.
7. The imported file is kept, so a revision can be audited later.

## Schema

`migrations/0008_boms.sql`

```sql
CREATE TABLE project (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  name_norm TEXT NOT NULL UNIQUE,
  description TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE bom_revision (
  id INTEGER PRIMARY KEY,
  project_id INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  label TEXT NOT NULL,                 -- what the operator calls this revision
  source_filename TEXT NOT NULL,
  source_sha256 TEXT NOT NULL,
  stored_path TEXT,                    -- relative to the asset root, like part assets
  line_count INTEGER NOT NULL,
  imported_at TEXT NOT NULL,
  imported_by TEXT NOT NULL,
  note TEXT,
  UNIQUE (project_id, source_sha256)   -- the same file twice is not a revision
);

CREATE TABLE bom_line (
  id INTEGER PRIMARY KEY,
  revision_id INTEGER NOT NULL REFERENCES bom_revision(id) ON DELETE CASCADE,
  part_id INTEGER REFERENCES part(id) ON DELETE SET NULL,   -- NULL = unmatched
  mpn TEXT NOT NULL,
  mpn_norm TEXT NOT NULL,
  manufacturer TEXT,
  manufacturer_norm TEXT,
  description TEXT,
  value TEXT,
  footprint TEXT,                      -- as KiCad wrote it
  package TEXT,                        -- normalised, for grouping and display
  quantity INTEGER NOT NULL,
  references_json TEXT NOT NULL DEFAULT '[]',
  dnp INTEGER NOT NULL DEFAULT 0,
  match_status TEXT NOT NULL CHECK (match_status IN ('matched','unmatched','ambiguous')),
  match_note TEXT,
  created_at TEXT NOT NULL
);
CREATE INDEX bom_line_revision_idx ON bom_line(revision_id);
CREATE INDEX bom_line_part_idx ON bom_line(part_id);
```

Revisions are immutable. Correcting a BOM means importing a corrected file and
getting a new revision; there is no edit path on lines.

## Parsing

KiCad's BOM export is a CSV whose headers depend on the version and the columns
the operator ticked. The parser therefore maps header *aliases*, not positions:

| field | accepted headers |
|-------|------------------|
| references | Reference, References, Designator, Designators, Ref |
| quantity | Qty, Quantity, Count |
| value | Value, Comment |
| footprint | Footprint, Package |
| mpn | MPN, Manufacturer Part Number, Mfr Part #, Part Number, Supplier Part Number |
| manufacturer | Manufacturer, Mfr, Mfr. |
| description | Description, Desc |
| dnp | DNP, Do Not Populate, Exclude from BOM |

- Delimiter is sniffed among `,`, `;` and tab.
- Headers are matched case-insensitively after stripping spaces and punctuation.
- A file with no recognisable MPN column is refused with the list of headers it
  actually saw — that is the error an operator can act on.
- Reference lists are split on `,`, `;`, whitespace and expanded from ranges
  (`C1-C3` → `C1, C2, C3`). Sorted naturally (C2 before C10).
- `quantity` is the number of references when references exist; a stated Qty
  that disagrees is recorded in `match_note`, because the disagreement is a real
  defect in the BOM and someone should see it.
- Rows are collapsed by `(mpn_norm, manufacturer_norm)`; references merge and
  quantities add. Two rows that differ only by value or footprint keep that
  difference in `match_note`.
- DNP lines are kept and marked. They are not stock, but they are part of the
  design and the diff has to be able to show them changing.

## Matching

A line matches a part on `(mpn_norm, manufacturer_norm)`. When the BOM has no
manufacturer, it matches on `mpn_norm` alone, and only when exactly one part
carries that MPN — otherwise the line is `ambiguous` and says so.

Unmatched and ambiguous lines are first-class: they appear in the revision, they
count in the diff, and the project page reports them as a number that has to
reach zero before the BOM is usable.

**Footprint wins.** When a matched part's package is empty, or differs from the
KiCad footprint's normalised form, the part is updated to the KiCad value and
the change is recorded on the line's `match_note`. The board is the authority;
the distributor string is a description of a package, not a constraint.

## Import flow

1. `POST /api/projects/{id}/boms?dry_run=1` with the CSV: parse, match, compute
   the diff against the newest revision, store nothing.
2. The response is the same shape as the committed result, with
   `"dry_run": true` and no `revision_id`.
3. `POST` without `dry_run` writes the revision, its lines and the file under
   `boms/<project>/<sha256>.csv`.
4. Re-importing a byte-identical file returns **409** naming the existing
   revision; the work was already done.

### Diff shape

```json
{
  "revision": {"label": "rev C", "imported_at": "...", "line_count": 52},
  "previous": {"label": "rev B", "imported_at": "..."},
  "added": [{"mpn": "...", "quantity": 3, "references": ["R1","R2","R3"]}],
  "removed": [...],
  "changed": [{"mpn": "...", "from": {"quantity": 3}, "to": {"quantity": 4},
               "references_added": ["R9"], "references_removed": []}],
  "unchanged_count": 45,
  "unmatched": [{"mpn": "...", "manufacturer": null, "quantity": 1}]
}
```

Lines are keyed by `(mpn_norm, manufacturer_norm)`. The first revision has no
previous: every line is `added`.

## API

| method | path | notes |
|--------|------|-------|
| `GET`  | `/api/projects` | list with revision count and unmatched count of the newest revision |
| `POST` | `/api/projects` | `{name, description?}`; 409 on a duplicate name |
| `GET`  | `/api/projects/{id}` | project, revisions, newest diff summary |
| `POST` | `/api/projects/{id}/boms` | multipart `file`, `label`, `note?`, `dry_run?` |
| `GET`  | `/api/revisions/{id}` | lines, with part IPN where matched |
| `GET`  | `/api/revisions/{id}/diff` | diff against the previous revision |
| `POST` | `/api/bom-lines/{id}/resolve` | `{ipn}` to attach a line to an existing part |
| `POST` | `/api/revisions/{id}/resolve-unmatched` | create parts for every unmatched line |

Writes are `engineer`; creating projects and resolving is `admin`? No —
`engineer` throughout. Reads are `viewer`.

## CLI

```
shelfmark bom import --project "sk-sensor" --file BOM.csv --label "rev C"
shelfmark bom import --project "sk-sensor" --file BOM.csv --label "rev C" --dry-run
shelfmark bom list --project "sk-sensor"        # revisions, counts, unmatched
```

`--project` creates the project when it does not exist. The CLI is how a build
gets imported from a machine that already has the CSV, without a browser.

## Interface

- `/projects` — list, with newest revision and unmatched count.
- `/projects/{id}` — revisions newest first, the latest diff inline, an import
  form (file input + label), and the unmatched lines with a resolve control.
- `/revisions/{id}` — every line: references, MPN, manufacturer, quantity,
  package, and a linked IPN or a "match" action.

The import form posts to the HTML route, not the API, and renders the diff as a
confirmation step before committing: *"52 lines, 3 added, 1 removed, 5 unmatched
— import as rev C?"*

## Out of scope

Placement files, pick-and-place export (M6), supplier offers on lines (M2),
alternative parts (M4), and editing a revision after import.
