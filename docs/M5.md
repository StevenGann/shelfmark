# M5 — Stock: where it is, how many

The parts table answers "what is this". It cannot answer "how many do I have,
and where", which is the question that stops a build. This milestone adds a
quantity per location and a ledger of every change, and nothing else.

## Definition of done

1. A part page shows total on hand and a row per location.
2. A person can record a receipt, a consumption, an adjustment to a counted
   quantity, and a move between locations — from a phone, one-handed.
3. Every quantity change is a ledger row naming who did it and why.
4. `stock_item.quantity` always equals the sum of that item's own move deltas —
   including moves, which is why a move writes two opposing rows.
5. The parts list shows on-hand counts, so a shortage is visible without
   opening a part.
6. A move that would take an item below zero is refused, not silently clamped.
7. Locations are typed freely and reused from a suggestion list.
8. `/api` exposes the same facts for machines.

## Schema

`app/migrations/0007_stock.sql`

```sql
CREATE TABLE stock_item (
  id INTEGER PRIMARY KEY,
  part_id INTEGER NOT NULL REFERENCES part(id) ON DELETE CASCADE,
  location TEXT NOT NULL,            -- as typed, trimmed, spaces collapsed
  location_norm TEXT NOT NULL,       -- lower(trim(collapsed)), for matching
  quantity INTEGER NOT NULL DEFAULT 0 CHECK (quantity >= 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (part_id, location_norm)
);

CREATE TABLE stock_move (
  id INTEGER PRIMARY KEY,
  stock_item_id INTEGER NOT NULL REFERENCES stock_item(id) ON DELETE CASCADE,
  kind TEXT NOT NULL CHECK (kind IN
    ('receive','consume','adjust','scrap','build','move')),
  delta INTEGER NOT NULL,            -- signed; a move writes -q here and +q there
  resulting_quantity INTEGER NOT NULL,
  note TEXT,
  actor TEXT NOT NULL,               -- username, or a key's name for API callers
  created_at TEXT NOT NULL
);
CREATE INDEX stock_move_item_idx ON stock_move(stock_item_id, created_at);
CREATE INDEX stock_item_location_idx ON stock_item(location_norm);
```

`location_norm` is `lower(trim(collapse_spaces(location)))`. Case is preserved
in `location` because "Drawer A" reads better than "drawer a", but "Drawer A"
and "drawer  a" are the same bin.

Moving stock between locations is double entry, not a special case: the ledger
gets two `move` rows, `-quantity` on the source and `+quantity` on the
destination, both naming the other end. The part's total is unchanged and every
stock item still satisfies `quantity == SUM(delta)` for its own rows. When the
destination has no row it is created and merged into, because free text means
two spellings can become one bin.

## Rules

- **No negative stock.** `consume`, `scrap` and `build` beyond the quantity are
  refused with 409 and the row is untouched. If the shelf and the record
  disagree, the answer is a count: `adjust`.
- **`adjust` takes the counted number, not a delta.** The UI asks "how many are
  actually there", computes the difference, and stores the delta in the ledger.
  This makes recounts normal rather than exceptional.
- **One transaction per move.** `BEGIN IMMEDIATE`, read the row, check, insert
  the move, update the quantity, commit — the same shape as IPN allocation.
- **Actor is recorded.** Sessions give a username; API keys give the key's name.
- **Deleting a part deletes its stock** (cascade) but the ledger is history and
  goes with it; there is no global audit trail in this milestone.

## API

| method | path | body / notes |
|--------|------|--------------|
| `GET`  | `/api/parts/{ipn}/stock` | `{total, items: [{location, quantity, updated_at}]}` |
| `POST` | `/api/parts/{ipn}/stock/moves` | `{location, kind, quantity, note?}` — `quantity` is positive for receive, positive-for-consume (the sign comes from `kind`), and the counted total for `adjust` |
| `GET`  | `/api/stock?location=&q=&below=` | rows across parts; `below` finds low stock |
| `GET`  | `/api/locations` | distinct locations with item counts, for suggestions |
| `POST` | `/api/stock/move` | move a quantity between two locations |

All require the `engineer` role for writes, `viewer` for reads.

## Interface

**Part page.** A stock panel under the part:

```
On hand: 47

0402 bin A     12    [+ receive] [− consume] [count]
Shelf 3 box 2  35    [+ receive] [− consume] [count]
                   [move to…]
```

The actions open an inline form (no modal): quantity, note, submit. 44 px
targets, 16 px inputs, one column at 390 px.

**`/stock`.** Every stock row, grouped by location, with a search box and a
"below N" filter. This is the page you open when you are standing in front of
the shelves.

**Parts list.** An "On hand" column showing the total; blank means zero, not
unknown. Sorting by on-hand is a link.

## Also in this milestone

Two operational gaps that are not features but are owed:

- **`shelfmark user`** — `list`, `create`, `passwd`, `disable`, `enable`, `role`.
  An admin who forgets a password on a box with no email is otherwise locked
  out; this is the break-glass path.
- **Queue tick** — the app drains `fetch_job` on a timer inside the lifespan
  (every 15 minutes, one pass, no overlap with a running pass), so enrichment
  no longer depends on somebody running the CLI.

## Out of scope

Reservations for builds (M6), lot/date tracking, serial numbers, barcode
scanning, and multi-warehouse hierarchy. Location stays a string because real
shelves are not a taxonomy.
