# M6 — Builds and the OpenPnP handoff

A BOM revision says what a board needs. A build says *we are making N of them*, and this milestone
makes Shelfmark answer three questions in order:

1. **Do we have the parts?** — per line, required against on hand, with substitutes that can cover.
2. **Take them.** — committing a build consumes stock, atomically, never into the negative.
3. **Hand it to the machine.** — a pick list and an OpenPnP board/job file.

Everything here is downstream of M3 (BOM), M4 (substitutes) and M5 (stock). Nothing new is
invented: a build is a view over lines that already exist.

## Data

```sql
-- 0011_builds.sql
CREATE TABLE build (
  id            INTEGER PRIMARY KEY,
  revision_id   INTEGER NOT NULL REFERENCES bom_revision(id) ON DELETE CASCADE,
  boards        INTEGER NOT NULL CHECK (boards > 0),
  status        TEXT NOT NULL DEFAULT 'planning',   -- planning | committed | abandoned
  note          TEXT,
  created_by    TEXT NOT NULL,
  created_at    TEXT NOT NULL,
  committed_at  TEXT
);

CREATE TABLE build_line (
  id           INTEGER PRIMARY KEY,
  build_id     INTEGER NOT NULL REFERENCES build(id) ON DELETE CASCADE,
  bom_line_id  INTEGER NOT NULL REFERENCES bom_line(id) ON DELETE CASCADE,
  part_id      INTEGER REFERENCES part(id) ON DELETE SET NULL,
  required     INTEGER NOT NULL,   -- per-board quantity x boards
  consumed     INTEGER NOT NULL DEFAULT 0,
  short        INTEGER NOT NULL DEFAULT 0,   -- as of the last plan
  UNIQUE (build_id, bom_line_id)
);

CREATE TABLE placement (
  id           INTEGER PRIMARY KEY,
  revision_id  INTEGER NOT NULL REFERENCES bom_revision(id) ON DELETE CASCADE,
  reference    TEXT NOT NULL,
  side         TEXT NOT NULL DEFAULT 'Top',
  x_mm         REAL NOT NULL,
  y_mm         REAL NOT NULL,
  rotation_deg REAL NOT NULL DEFAULT 0,
  package      TEXT,
  value        TEXT,
  UNIQUE (revision_id, reference)
);
```

`build_line.consumed` is a number to show, not a second ledger — the truth stays in
`stock_move`, and a committed build's moves carry `ref = 'build:<id>'` in their `note`
(`build 7 of 10`), so the ledger can always be read back to the build.

## Planning

`POST /api/projects/{project_id}/boms/{revision_id}/builds` body `{"boards": 10, "note": "..."}`
returns the build with its lines. For every non-DNP `bom_line`:

- `required = bom_line.quantity * boards` (the quantity is per board; M3 already expanded
  references, so a line of 12 resistors with `quantity` 3 means three per board).
- `part_id` is the matched part of the line, or NULL when the line is unmatched.
- `short = max(0, required - on_hand(part))`, where on hand is summed across all locations.
- unmatched lines are **carried into the build** with `part_id` NULL and `required` set, and
  they always count as short: you cannot build a board with a line nobody can buy. The build
  page states how many lines are unmatched rather than pretending they are fine.

A plan changes nothing. Creating a second identical plan is allowed; it is a question, not an
action.

### Substitute coverage

For each short line, look at M4's links **from** the line's part and list any substitute with
stock, in the same shape the revision page uses:

```
short 40 — SK-00012 equivalent (200 on hand) covers
short 40 — SK-00019 form-fit (0 on hand)
```

The build page does not auto-substitute. A substitute is a claim about the board and a human
makes it (M4's rule); that human then links the parts, and replans.

## Committing

`POST /api/builds/{id}/commit` body `{"locations": {"<build_line_id>": "Bin 12", ...}}` optional.

For each line with `part_id` and `required > 0`:

1. Draw `required` units from that line's preferred location when given, otherwise from the
   locations with the most stock first (ties: alphabetically, so the run is reproducible).
2. Each draw is a `stock_move` of kind `build`, negative, with
   `note = "build <id> of <boards>"`.
3. The whole build is one `BEGIN IMMEDIATE` transaction. If any line cannot be filled, the
   response is **409** naming the first line that could not be covered:
   `SK-00021 0402 10k: need 120, have 87 — 33 short`, and nothing is written.

Committed builds are immutable. `POST /api/builds/{id}/abandon` marks a planning build abandoned;
it cannot touch a committed one.

**Why all-or-nothing:** a half-consumed build leaves the ledger describing a board that was
never made, and the next person cannot tell whether the missing parts went onto a board or into
a drawer.

## Positions

`POST /api/revisions/{revision_id}/positions` with a KiCad position file (`.pos`) replaces that
revision's placements.

**Two file shapes, because KiCad writes both.** The default `.pos` export is *padded columns*, not
CSV, and the real `symkin_sensor-all.pos` is exactly this:

```
### Footprint positions - created on 2026-07-08T23:34:18 ###
## Unit = mm, Angle = deg.
# Ref     Val                     Package                       PosX       PosY       Rot  Side
C202      2.2uF                   C_0402_1005Metric         130.1500   -56.3000    0.0000  bottom
```

There is no delimiter to sniff, so a row is read from the right: `Side`, `Rot`, `PosY` and `PosX`
are the last four tokens and the package is the one before them. A value that contains a space
(`10k 1%`) shifts the columns without breaking that. The CSV export (comma, semicolon or tab) is
parsed by header aliases:

| field | accepted headers |
|---|---|
| reference | `Ref`, `Reference`, `Designator` |
| value | `Val`, `Value`, `Comment` |
| package | `Package`, `Footprint` |
| x | `PosX`, `Mid X`, `X` |
| y | `PosY`, `Mid Y`, `Y` |
| rotation | `Rot`, `Rotation` |
| side | `Side`, `Layer` |

Rows with an unparseable coordinate are refused with the line number and the text. `side` is
normalised to `Top`/`Bottom`; `bottom` and `B` both mean Bottom. A `#` comment line is skipped.
Importing is idempotent per revision: a re-import replaces, and gives the file's sha256 in the
response so the operator can see it changed or did not.

Positions are optional. Without them a build still commits and still produces a pick list, but
the OpenPnP file cannot be produced and the endpoint says exactly that (409, `positions_required`).

## Exports

All three are downloads on the build page and routes on the API, `GET`-only, available to
**viewer** role, because they change nothing.

### `GET /builds/{id}/picklist.csv`

```
ipn,mpn,manufacturer,package,value,required,on_hand,location,substitutes
SK-00021,RC0402FR-0710KL,Yageo,0402,10k,120,200,"Bin 12",SK-00044 equivalent
```

One row per line that has a part. Unmatched lines are appended with an empty `ipn` and the BOM's
MPN/manufacturer text, so the list is complete.

### `GET /builds/{id}/board.xml`

The OpenPnP board format, taken from the shipped sample
`openpnp/openpnp/samples/EAT001/EAT001.board.xml`:

```xml
<openpnp-board name="sk-sensor-rev-B.board.xml">
   <outline units="Millimeters"/>
   <fiducials/>
   <placements>
      <placement version="1.1" id="C7" side="Top" part-id="SK-00021" type="Place">
         <location units="Millimeters" x="12.4" y="24.4" z="0.0" rotation="180.0"/>
      </placement>
   </placements>
</openpnp-board>
```

- `id` is the schematic reference, `part-id` is the Shelfmark IPN.
- `side` comes from the position file. `rotation` is written as given in degrees.
- DNP lines never appear; a placement with no matching line is skipped and counted in
  `X-Skipped-Placements`.
- `type` is `Place` for every part that has an IPN.

### `GET /builds/{id}/job.xml`

```xml
<openpnp-job>
   <board-locations>
      <board-location side="Top" board-file="sk-sensor-rev-B.board.xml">
         <location units="Millimeters" x="0.0" y="0.0" z="0.0" rotation="0.0"/>
      </board-location>
   </board-locations>
</openpnp-job>
```

**Stated limitation, in the doc and on the page:** this is a *placement* file. OpenPnP still
needs a part in its own library for each `part-id` before it can place anything — Shelfmark knows
the inventory, not the nozzles, feeder offsets or package geometry. The pick list is what the
operator uses to create those parts; the file is what stops them typing coordinates by hand.

A job names the board **once**, whatever the build count. Repeating the board location per board
would stack every copy at 0,0 and place them on top of each other; where the other nine boards sit
is the operator's panel, not Shelfmark's. The build page says so: *placements describe one board;
OpenPnP's board count sets the rest*.

## API

| method | path | role |
|---|---|---|
| POST | `/api/projects/{pid}/boms/{rid}/builds` | engineer |
| GET | `/api/builds` | viewer |
| GET | `/api/builds/{id}` | viewer |
| POST | `/api/builds/{id}/commit` | engineer |
| POST | `/api/builds/{id}/abandon` | engineer |
| POST | `/api/revisions/{rid}/positions` | engineer |
| GET | `/api/builds/{id}/picklist.csv` | viewer |
| GET | `/api/builds/{id}/board.xml` | viewer |
| GET | `/api/builds/{id}/job.xml` | viewer |

HTML pages: `/builds`, `/builds/{id}` (lines, short, substitutes, commit button, downloads),
a *Plan a build* form on `/revisions/{id}`, and a positions upload on the same page.

CLI: `shelfmark build plan <revision-id> --boards N`, `shelfmark build commit <id>`,
`shelfmark build list`, `shelfmark build export <id> --out DIR`.

## Tests

- plan arithmetic: per-board × boards, DNP excluded, unmatched carried and short
- a plan writes no stock rows
- commit consumes exactly `required` per line and leaves the invariant `quantity == SUM(delta)`
- commit refuses 409 when short, writing **no** rows at all (checked with a second line that
  *could* have been filled)
- commit prefers the named location, then the largest
- a committed build cannot be committed twice (409) or abandoned (409)
- substitute coverage: a short line lists a linked substitute with stock and `covers`
- pick list includes unmatched lines with an empty ipn
- positions: KiCad headers parse, a bad coordinate names the line, re-import replaces
- board.xml: one placement per position, DNP skipped, `part-id` is the IPN, well-formed XML
- board.xml without positions → 409 `positions_required`
- viewer can download, viewer cannot commit
