# M7 — Export, restore and scheduled backup

Status: shipped 2026-11-26. Depends on M1–M6.

## The problem

Everything Shelfmark knows lives in one file on one volume. There is no export, no restore and no
backup. A corrupted page, a mistaken `DELETE`, a bad migration or a dead disk takes the inventory,
the BOM history and the stock ledger with it, and there is nothing to load back.

Copying `/data` by hand is the current answer. It works until someone copies a database mid-write
and leaves the WAL behind, or copies it while the app is running.

## Goals

1. One command produces a single portable file: the database as data, plus the assets.
2. One command loads that file into an empty instance and proves it arrived intact.
3. A nightly job keeps a fortnight of bundles on the NAS, without a human remembering.
4. The offer refresh is actually scheduled — `enrich --stale-days` exists but nothing calls it.

## The bundle

A `.zip`, because it streams, needs no external tooling and can be opened by anything.

```
shelfmark-20261126T031700Z.zip
├── manifest.json
├── data.json
└── assets/…
```

**`manifest.json`**

```json
{
  "format": 1,
  "app": "shelfmark",
  "version": "0.1.0",
  "created_at": "2026-11-26T03:17:00Z",
  "counts": {"part": 87, "bom_line": 108, "…": 0},
  "data_sha256": "…",
  "asset_files": 143,
  "asset_bytes": 41943040
}
```

`data_sha256` is the SHA-256 of `data.json` as stored. A restore recomputes it before touching the
database: a bundle that fails its own checksum is refused rather than half-loaded.

**`data.json`**

```json
{"format": 1, "tables": {"app_user": [{…}], "part": [{…}], …}}
```

Rows are plain objects keyed by column name, in primary-key order. Ids are preserved: every foreign
key in the bundle points at an id in the same bundle.

Tables, in restore order (parents before children):

`app_user`, `api_key`, `distributor`, `manufacturer`, `part`, `part_link`, `part_asset`,
`part_substitute`, `offer`, `price_break`, `project`, `bom_revision`, `bom_line`, `build`,
`build_line`, `stock_item`, `stock_move`, `placement`, `machine`, `fetch_job`, `ipn_counter`

Two tables are deliberately excluded:

- `user_session` — sessions are live state, not data. Restoring them would resurrect logins that
  were meant to be gone.
- `schema_migration` — the target database runs its own migrations on start. Importing a ledger
  from elsewhere would let a bundle claim migrations the target never applied.

`ipn_counter` is included, so restored parts do not collide with the next internal part number.

**Assets** are stored under `assets/<relative path>`, byte-identical, using the same relative paths
the app writes (`parts/<ipn>/<name>`). They are optional: `--no-assets` produces a smaller bundle
when only the rows matter.

## Restore

`shelfmark restore <bundle> [--force]`

1. Open the zip, read `manifest.json`, refuse an unknown `format` or `app`.
2. Recompute `data_sha256`; refuse on mismatch, naming both hashes.
3. Refuse a non-empty target — any row in `part`, `project`, `app_user` or `stock_item` — unless
   `--force` is given. `--force` deletes the current rows in the bundle's tables first, inside the
   same transaction, so a failed restore leaves the previous data in place.
4. Insert every table in the order above, one transaction.
5. Reset `sqlite_sequence` for each table that has an autoincrement id, to the bundle's maximum.
6. Run `PRAGMA foreign_key_check`; a single row aborts the transaction.
7. Compare per-table counts against the manifest; a mismatch aborts.
8. Extract assets after the commit, each file written to a temporary name and renamed, never
   deleting an existing asset.

A restore prints one line per table (`part 87 ok`) and a final `restored 21 tables, 143 assets`.

## CLI

```
shelfmark export  --out FILE [--no-assets]
shelfmark restore FILE [--force]
shelfmark backup  --dir DIR [--keep 14] [--no-assets]
```

`backup` is the scheduled form: it writes `DIR/shelfmark-<stamp>.zip`, then deletes the oldest
bundles beyond `--keep`, and prints the path it wrote. It returns 1 if the bundle it just wrote
cannot be re-opened.

## API

`GET /api/export` — admin only, streams the same zip with `Content-Disposition: attachment`. It
carries credentials (users, API key hashes), so it is never available to the `viewer` role and the
response sets `Cache-Control: no-store`.

## Schedule

Two CronJobs in the homelab repo, not an in-app timer: a timer inside the app stops when the app is
unhealthy, and restarts the retention window from scratch.

- `shelfmark-backup`, daily at 03:17 UTC — mounts the data volume read-only and the NAS backup
  directory, runs `shelfmark backup --dir /backups --keep 14`.
- `shelfmark-offers`, Mondays at 04:05 UTC — runs `shelfmark offers refresh --all --stale-days 30`, with
  the same DigiKey secret as the deployment.

Both use the same image tag as the deployment and the same non-root security context.

## Verification

`tests/test_archive.py`:

- export → restore into a second, empty data directory → every table count matches and
  `foreign_key_check` is clean
- an asset written before the export exists byte-identical after the restore
- a bundle whose `data.json` was altered is refused with a checksum error
- a restore into a populated database is refused without `--force`
- `backup --keep 2` leaves two bundles after three runs
- `GET /api/export` is 403 for a viewer key and 200 with a zip for an admin key

The suite stays above the 83% coverage gate.

## Acceptance

- `shelfmark export` on the live pod produces a bundle whose counts match the live database.
- `shelfmark restore` into a scratch instance returns a database the app serves without error, with
  the same part count, BOM line count and stock quantities.
- The nightly CronJob has run at least once and left a bundle on the NAS.
- `shelfmark offers refresh --all --stale-days 30` runs from the CronJob without the app being restarted.
- README and `docs/CLI.md`, `docs/API.md` describe all of the above.

## Out of scope

Point-in-time recovery, incremental backups, encryption at rest, and cross-version migration of old
bundles. A bundle from a different `format` is refused, not translated.
